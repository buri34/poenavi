# ぽえとれ NDLOCR常駐化・読取状況表示 実装計画

- 作成日: 2026-09-25
- 状態: **Mac側実装・回帰確認済み／Windows実機受入待ち**
- 対象: PoE2「アビス冒涜Modティアチェック」
- 前提コミット: `5ea0e4fecb`

## 1. 背景と確認済み事実

現在のぽえとれは、Windows OCRでTierを確定できず、かつ数値だけが欠落した安全な候補に限って
NDLOCR-Lite 1.3.1を使う。認識結果の採用条件は既に限定されており、Windows OCRで確定した結果を
NDLOCRが上書きすることはない。

現在の`PoENaviNdlOcr.exe`はリクエストごとに起動して終了するため、NDLOCRが必要な回は毎回モデルを
読み直し、実プレイログでは約13～17秒を要した。

Windows実機の常駐検証では次を確認した。

- モデル起動完了まで: 約11.87秒
- 常駐後の推論: 0.67～0.91秒、平均約0.75秒
- `物理ダメージが64%増加する`: 5回すべて認識成功
- 常駐中Working Set: 約781MiB、ピーク約800MiB
- 5分放置してもRAMはほぼ減らない

このため、常時起動は避け、NDLOCRが必要になった時だけ起動し、短時間だけ再利用する。

## 2. 目的

1. 初回のNDLOCR利用後、連続Unveil中の2回目以降を約1秒前後へ短縮する。
2. NDLOCR利用後、冒涜チェックの操作が3分間なければプロセスを終了し、約0.8GBの物理RAMを返す。
3. 初回の約10～15秒間、ゲーム画面上に理由と進行中であることを表示する。
4. Windows OCR優先・NDLOCR数字救済限定という現在の安全境界を維持する。
5. ユーザーへの追加インストール、追加ダウンロード、設定操作を発生させない。

## 3. 対象外

- Windows OCRとNDLOCRの採用ルール変更
- NDLOCRによる全文置換や、本文が不安定なケースの自動救済
- PoENavi起動時からのNDLOCR常駐
- GPU利用
- NDLOCRモデル・ライセンス・配布形式の変更
- 設定画面への常駐時間変更UI（初版は180秒固定）

## 4. 確定仕様

### 4.1 起動と終了

- Windows OCRでTierが確定した場合、NDLOCRを起動しない。
- 数字救済候補が1件以上出た時だけNDLOCRを遅延起動する。
- 起動済みなら同じプロセスとロード済みモデルを再利用する。
- **最後のNDLOCRリクエスト完了から180秒**を基本の終了時刻とする。
- NDLOCRが既に起動している場合、アビス冒涜Modチェックのホットキーが有効な操作として受付された
  時点でも、終了時刻をその時点から180秒後へ延長する。
- ここでいう「受付」は、ぽえとれの画面読取機能と冒涜チェックが有効で、ホットキー処理から
  `capture_desecration_tiers()`を経由して冒涜コントローラーへ読取要求が渡った時点とする。
- NDLOCRが起動していない状態で冒涜チェックのホットキーを押しても、タイマー更新のためだけには
  起動しない。実際に数字救済候補が出た時だけ初回起動する。
- エクスペディション報酬チェックなど、他のWindows OCR機能ではNDLOCRの終了時刻を延長しない。
- 180秒以内にNDLOCRを再利用した場合は、リクエスト完了時点から改めて180秒へリセットする。
- ぽえとれ終了、画面読取機能OFF、PoE1/PoE2モード切替、自動更新開始時は即時終了する。
- 親プロセスが異常終了した場合も、標準入力のEOFを検出して子プロセスが終了する。

### 4.2 ゲーム画面上の案内

NDLOCRへ切り替える時だけ、選択肢パネル右上側（実画像で確認した赤枠相当）に、
半透明の非操作・非フォーカス型ステータスオーバーレイを表示する。

初回起動時の文言:

> 通常の読み取りで一部の数値を確認できませんでした<br>
> 高精度OCRを準備しています…<br>
> 初回のみ10～15秒ほどかかります

3分以内の再利用時の文言:

> 通常の読み取りで一部の数値を確認できませんでした<br>
> 高精度OCRで再確認しています…

表示規則:

- 初回起動時は即時表示する。
- 常駐再利用時は、NDLOCRへリクエストを送ると同時に400msの単発タイマーを開始する。
- 400ms経過時点で「同じスキャン世代・同じrequest IDのNDLOCR応答待ち」が続いている場合だけ、
  2行の再確認表示を出す。
- 400msより前に応答、失敗、キャンセル、スキャン世代変更のいずれかが起きた場合はタイマーを
  取り消し、再確認表示を一度も出さない。
- 400ms後に表示した場合は、そのリクエストの応答、失敗、キャンセル時に直ちに消す。
- 処理成功、拒否、失敗、スキャン世代変更、コントローラー終了のいずれでも必ず消す。
- 小さなスピナーを表示し、停止ではなく処理中であることを示す。
- PoEや既存オーバーレイからフォーカスを奪わず、マウス入力を透過する。
- キャプチャ範囲上端の右側を基準に配置し、ゲームクライアント領域外へ出ないよう補正する。
- Tierバッジ、カテゴリ選択、既存15秒自動消去とは別の短命な表示として管理する。

## 5. 実装設計

### 5.1 NDLOCRヘルパー

配布サイズを増やさないため、新しい巨大なEXEを追加せず、既存の
`tools/NDLOcrLite/PoENaviNdlOcr.exe`を拡張する。

- PoENavi用の薄いエントリーポイントを追加する。
- 現在の一回実行CLIはビルド時スモークテスト互換のため維持する。
- 製品利用では`--server`モードで起動する。
- 起動時に4つのONNXセッションを一度だけ作成する。
- 標準入力でJSON Linesをブロッキング待機し、待機中のポーリングCPUを発生させない。
- 標準出力はプロトコルJSON専用、診断は標準エラーへ分離する。
- `ready`、`recognize`、`shutdown`の3種類を扱う。
- 画像は親側のセッション一時フォルダへBMPとして保存し、JSONではファイルパスとrequest IDを渡す。
- 応答はrequest ID、本文、最低confidence、推論時間、エラーを返す。
- 標準入力EOFまたは`shutdown`でモデルを解放して終了する。

### 5.2 親プロセス側ライフサイクル

`src/poetore/poe2/ndlocr_lite.py`の`NdlOcrLiteServer`を、次の責務を持つ管理クラスへ変更する。

- `Popen`による遅延起動と`CREATE_NO_WINDOW`
- 起動済み・準備中・停止済みの状態管理
- stdout読取専用スレッドとrequest IDごとの応答待ち
- stderrの排出と、OCR本文を含めない診断要約
- 同時リクエストの直列化
- 起動／応答タイムアウト時の強制終了と次回再起動
- 180秒のアイドルタイマー
- リクエスト一時ファイルとセッションディレクトリの削除
- `close()`での`shutdown`送信、短時間待機、未終了時kill

タイマーと終了処理は同じロック／世代番号で保護し、リクエスト中に古いタイマーが新しい
プロセスを終了しないようにする。

### 5.3 冒涜コントローラーとの接続

`DesecrationTierController`は現在の候補抽出・採用判定を変えず、NDLOCR呼出し前後にUI通知を追加する。

冒涜チェックのホットキー受付時には、NDLOCR管理クラスの`touch_if_running()`相当を呼ぶ。
この操作は起動済みプロセスのアイドル期限だけを更新し、停止中のNDLOCRを起動しない。
エクスペディション側のコントローラーからはこの操作を呼ばない。

1. Windows OCRと英語数値OCRを実行する。
2. 現在と同じ`ndl_numeric_candidate_indexes()`で候補を抽出する。
3. 候補がなければNDLOCRも案内表示も行わない。
4. 候補があれば、常駐状態に応じた案内表示をGUIスレッドへSignalで依頼する。
5. NDLOCRを呼び、現在と同じ`apply_ndl_numeric_rescues()`で安全に採否を決める。
6. 採否にかかわらず案内を消し、既存のTier解決・閉じた範囲再試行へ戻る。

スキャンが古くなった場合は結果を画面へ反映しない。モデル起動自体が完了した場合は次回利用のため
常駐を継続できるが、画面案内は必ず消す。

### 5.4 パフォーマンスログ

OCR本文や画像は記録せず、既存の`poetore-performance.jsonl`へ次を追加する。

- `ndl_resident_start_requested`
- `ndl_resident_ready`: 起動所要時間
- `ndl_request_completed`: cold/warm、推論時間、候補数、採用数
- `ndl_request_failed`: 失敗種別のみ
- `ndl_resident_stopped`: `idle_timeout` / `controller_close` / `timeout` / `crash`

これにより、総所要時間とモデル起動・推論を分離して確認できるようにする。

### 5.5 配布ビルド

- 現在と同じNDLOCR-Lite 1.3.1、CPUランタイム、4モデル、CC BY 4.0・依存ライセンスを同梱する。
- ヘルパーは1本のままとし、モデルも複製しないため、配布ZIP容量は現状約465MiBから大きく増やさない。
- ビルド時スモークテストを常駐モードにも拡張し、`ready`、2回連続認識、`shutdown`を確認する。
- ZIP監査でヘルパー、4モデル、ライセンス、禁止ファイル不在を継続確認する。

## 6. 実装順序

1. **失敗回帰を先に追加**
   - 同一ヘルパーでモデルロードが1回だけになること
   - 180秒タイマーのリセットと終了
   - `close()`・EOF・異常時の終了
   - Windows成功時にNDLOCRが起動しないこと
2. **常駐プロトコルを実装**
   - ヘルパーのサーバーモード
   - 親側の起動・応答・終了管理
3. **案内オーバーレイを実装**
   - cold/warm文言、遅延表示、必ず消える終了経路
   - 非フォーカス・入力透過・画面端補正
4. **ログと配布工程を更新**
   - 起動と推論の時間分離
   - ビルドスモーク・ZIP監査
5. **Mac側回帰を完走**
6. **Windows変更不可ミラーで実ビルド・実プレイ確認**

## 7. テスト計画

### 7.1 単体・結合テスト

- Windows OCRだけでTier確定できる選択肢では、NDLOCRを一度も起動しない。
- `物理64%`の数字欠落だけがNDLOCR候補になり、T7へ復旧する。
- `51% → 5196`は現在どおり不採用で、Windows結果を上書きしない。
- cold startでは3行案内、warm startでは2行案内になる。
- warm処理が400ms以内なら案内を表示しない。
- 例外、timeout、閉じた範囲再試行、古いgeneration、画面読取OFF、ウィンドウ終了で案内が残らない。
- 最終更新から179秒では常駐、180秒到達で終了し、NDLOCR利用または有効な冒涜チェック受付で
  タイマーがリセットされる。
- 起動済みNDLOCRは、冒涜チェックのホットキー受付で、Windows OCRだけで完了した場合も
  アイドルタイマーが延長される。
- 停止中のNDLOCRは、冒涜チェックのホットキー受付だけでは起動しない。
- エクスペディション報酬チェックのホットキー、その他のWindows OCR利用、PoE外で無効化された
  ホットキー入力ではアイドルタイマーが延長されない。
- ぽえとれ終了時に子プロセスと一時ファイルが残らない。
- ヘルパー異常終了後、次のNDLOCR候補で再起動できる。

### 7.2 描画確認

- 実ゲーム画像へ案内を合成し、赤枠相当の位置、改行、文字サイズ、背景透過、スピナーを目視確認する。
- 1920x1080、2560x1440、3021x1296相当でゲーム領域外へはみ出さないことを確認する。
- PoEの操作・既存Tierバッジ・装備カテゴリ選択を妨げないことを確認する。

### 7.3 Windows実機受入

- 初回の`物理64%`で案内が即時表示され、約10～15秒後にT7が表示される。
- 3分以内の2回目はモデル再読込なしで完了し、目標2秒以内とする。
- NDLOCR利用後、3分以内に冒涜チェックのホットキーを押し続ける間は、各受付時点から3分後まで
  プロセスが維持される。各読取りがWindows OCRだけで完了しても同様とする。
- 同じ時間帯にエクスペディション報酬チェックだけを行っても、NDLOCRの終了時刻は変わらない。
- 最後のNDLOCR完了後、冒涜チェックの受付がないまま3分経過すると、NDLOCRプロセスが消え、
  Working Set約0.8GBが解放される。
- 3分経過後の次回はcold startになり、案内が再表示される。
- ぽえとれ終了直後、NDLOCRプロセスが残らない。
- 通常のWindows OCRだけの読取り速度（概ね1秒以内）に回帰がない。
- 完成ZIPは追加インストールなしで動作し、容量とSHA-256を記録する。

## 8. 失敗時の扱いとロールバック

- NDLOCRの起動・応答に失敗しても、PoENavi本体とWindows OCR結果は維持する。
- 失敗時は現在と同じ未解決表示または閉じた範囲再試行へ進み、アプリを落とさない。
- 常駐方式にプロセス残留・更新阻害・精度回帰があれば、親側を一回実行方式へ戻せるよう、
  採用判定ロジックと常駐ライフサイクルを分離する。
- ユーザー設定や保存データの移行は発生させない。

## 9. 実装開始前の合意事項

次を本計画の確定値とする。

- アイドル終了: **最後のNDLOCR完了、または起動中の冒涜チェック受付から3分**
- タイマー更新対象: アビス冒涜Modチェックだけ。エクスペディション等は対象外
- cold案内: 上記3行を即時表示
- warm案内: 上記2行を400ms遅延表示
- 常駐上限: 初版では設けず、NDLOCR利用または起動中の冒涜チェック受付ごとに3分タイマーを更新

- 配布: v4.4.0時点では既存ZIPへの自己完結同梱を維持
- 安全境界: Windows OCR優先、NDLOCRは数字欠落救済のみ

## 12. v4.4.1 配布方式の改訂（2026-09-25）

v4.4.0の本体ZIPは展開後約768.61MiBとなり、既存UpdaterのZIP爆弾対策上限512MiBを超えた。
既存ユーザーが将来どの版から更新しても同じ問題を起こさないよう、v4.4.1以降は次を確定仕様とする。

- `PoENavi.zip`からNDLOCR実行環境と4モデルを外し、展開後512MiB以下をビルド時に監査する。
- NDLOCR実行環境、4モデル、ライセンスを`PoENavi-HighAccuracyOCR.zip`として同じReleaseへ添付する。
- アビス冒涜Modチェックの管理画面を開いた時だけ、未導入または旧版のパックをバックグラウンド取得する。
- 管理画面内に準備、進捗、インストール、利用可能、エラーを表示し、エラー時だけ再試行操作を提供する。
- 管理画面を閉じてもPoENavi起動中は取得を続ける。PoENavi終了時は安全に中断し、次回管理画面表示時に再試行する。
- パックは`%LOCALAPPDATA%\PoENavi\ocr-packs\ndlocr-1.3.1`へ保存し、PoENavi更新後も再利用する。
- SHA-256、パス走査、リンク、ファイル数、単一ファイル、展開後総量、圧縮率を検証してから原子的に置換する。
- パック準備中はNDLOCRを待たずWindows OCRの結果を表示し、ダウンロード専用のゲーム内右肩表示は追加しない。
- パック準備完了後のNDLOCR採用条件、3分常駐、起動中表示は従来仕様を維持する。
